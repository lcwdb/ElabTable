# 第 02 项：搭建工作区

## AI协作方式

- AI 可以创建、维护教学 Markdown。
- 工程文件由你手写，终端命令由你运行。
- 每次只完成一个小步骤，反馈结果后继续。
- AI 不自行修改工程、安装依赖、运行项目或提交 Git；需要检查时以你的授权为准。
- 本文中的代码块是操作说明，不表示文件已经创建或命令已经运行。
- 每阶段验收后，由你执行 Git 提交；AI 协助解释与检查提交内容。

## 本次目标

建立 pnpm 工作区，理解根包与桌面包的关系，配置 Git 忽略、TypeScript 严格检查、ESLint 代码检查和 Prettier 格式检查。

本次不启动 Vue 或 Electron，也不创建云端服务。

## 第一步：创建根 package.json

在当前项目根目录 ElabTable 下，新建 `package.json`，手写：

```json
{
  "name": "elabtable",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "packageManager": "pnpm@11.22.0"
}
```

| 字段           | 含义                                                        |
| -------------- | ----------------------------------------------------------- |
| name           | 工程包名，使用小写，与 GitHub 仓库展示名称可以不同          |
| version        | 当前工程版本，从 0.1.0 开始                                 |
| private        | 防止误发布到 npm，不影响 Git 提交或 GitHub 上传             |
| description    | 描述文本：lcwdb的AI Agent工作台                             |
| type           | 当前包作用域中的 .js 文件使用 ES Module，采用 import/export |
| packageManager | 声明使用 pnpm 11.22.0；它本身不负责安装 pnpm                |

注意：JSON 不支持注释，最后一项后面不要加逗号。

**完成标志**：保存文件，编辑器没有 JSON 语法错误。先不用运行命令，把内容或完成情况发给 AI。

## 第二步：声明工作区

第一步确认后，在根目录新建 `pnpm-workspace.yaml`：

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

- `apps/*`：收纳可以独立启动的应用包，随后先建立 desktop，云端 server 留到第三阶段。
- `packages/*`：收纳可复用的包，例如后续的 contracts。
- `*` 只匹配这一层目录；被匹配的目录中应有自己的 package.json。
- YAML 使用空格缩进，不使用 Tab。

**完成标志**：根目录有根 package.json 和工作区声明。此时不必为了匹配规则创建所有目录。

## 第三步：建立桌面包

手动建立 `apps/desktop` 目录，在其中新建 `package.json`：

```json
{
  "name": "@elabtable/desktop",
  "version": "0.1.0",
  "private": true,
  "type": "module"
}
```

`@elabtable/desktop` 是包标识。前半部分是命名空间，后半部分是包名；不要求注册 npm 账号，目录也不必叫这个名称。

现在的目录应当是：

```text
ElabTable/
  package.json
  pnpm-workspace.yaml
  apps/
    desktop/
      package.json
```

原有 docs、prototype 和方案文件继续保留。

**完成标志**：能区分两个 package.json：根包负责协调和共用工具，desktop 包负责桌面应用自己的依赖与命令。

## 第四步：添加 Git 忽略规则

在根目录新建 `.gitignore`：

```gitignore
.DS_Store
node_modules/
dist/
out/
release/
coverage/
*.log
.env
.env.*
!.env.example
*.db
*.db-shm
*.db-wal
*.sqlite
*.sqlite-shm
*.sqlite-wal
*.sqlite3
*.sqlite3-shm
*.sqlite3-wal

```

依赖、生成物和本地数据库不应提交；`.env.example` 用来记录配置项名称和无敏感信息的示例，可以提交。

`.gitignore` 不会让已经被 Git 跟踪的文件自动退出跟踪。当前首次建立工程，先按这些规则起步，附件等实际路径确定后再补充。

**完成标志**：文件名以点开头，没有误建为 `.gitignore.txt`。

## 第五步：约束 Node 与 pnpm 版本

在根 `package.json` 中补充以下字段，保留其他内容：

```json
"engines": {
  "node": ">=24.19.0 <25",
  "pnpm": "11.22.0"
}
```

这是 JSON 片段，插入对象时注意相邻字段之间的逗号。

- Node 允许 24.19.0 及以上的 24.x 版本，不接受 25。
- pnpm 固定为 11.22.0；packageManager 声明工具选择，engines 声明版本要求。

将根 `pnpm-workspace.yaml` 补充为：

```yaml
packages:
  - 'apps/*'
  - 'packages/*'

engineStrict: true
```

`engineStrict` 顶格写，版本不满足要求时阻止安装。

运行以下命令确认本机环境：

```bash
node -v
pnpm -v
```

**完成标志**：本次实测分别为 v24.19.0 和 11.22.0，满足约束。

## 第六步：安装根包开发工具

先查询工具版本及运行要求：

```bash
pnpm view typescript version engines --json
pnpm view prettier version engines --json
```

本教程统一选用以下版本，先核验运行环境与 peer 范围，再安装整套工具，而不是分别追求每个包的最新版本。

| 工具                   | 版本    | 职责                       |
| ---------------------- | ------- | -------------------------- |
| typescript             | 6.0.3   | 类型检查                   |
| prettier               | 3.9.10  | 格式化                     |
| eslint                 | 10.13.0 | 代码质量检查               |
| @eslint/js             | 10.0.1  | JavaScript 推荐规则        |
| typescript-eslint      | 8.72.0  | TypeScript 解析与推荐规则  |
| eslint-config-prettier | 10.1.8  | 关闭与 Prettier 冲突的规则 |

当前 typescript-eslint 声明支持 TypeScript >=4.8.4 <6.1.0，因此选用 6.0.3；Node 24.19.0 满足这套工具的运行要求。版本以 2026-10-22 的查询为基线，不代表永久最新。

需要自行复核时运行：

```bash
pnpm view eslint@10.13.0 engines --json
pnpm view @eslint/js@10.0.1 peerDependencies --json
pnpm view typescript-eslint@8.72.0 engines peerDependencies --json
pnpm view eslint-config-prettier@10.1.8 peerDependencies --json
```

在根目录运行：

```bash
pnpm add -DwE typescript@6.0.3 prettier@3.9.10 eslint@10.13.0 @eslint/js@10.0.1 typescript-eslint@8.72.0 eslint-config-prettier@10.1.8
```

- `-D`：放入 devDependencies，属于开发与构建工具。
- `-w`：安装到工作区根包，供各包使用。
- `-E`：保存准确版本，不加 `^`。

验证安装：

```bash
pnpm exec tsc --version
pnpm exec prettier --version
pnpm exec eslint --version
```

**完成标志**：分别输出 Version 6.0.3、3.9.10 和 v10.13.0。

## 第七步：理解依赖声明与锁文件

根 `package.json` 会新增：

```json
"devDependencies": {
  "@eslint/js": "10.0.1",
  "eslint": "10.13.0",
  "eslint-config-prettier": "10.1.8",
  "prettier": "3.9.10",
  "typescript": "6.0.3",
  "typescript-eslint": "8.72.0"
}
```

它声明直接依赖。`pnpm-lock.yaml` 记录实际解析出的版本、间接依赖、依赖关系及下载内容校验信息。

重点观察锁文件的 `importers`：`.` 代表根包，`apps/desktop` 代表桌面包。根包下面的 devDependencies 中应出现上述六个工具。

- `specifier`：package.json 声明的要求。
- `version`：实际解析的版本。
- `packages`、`snapshots`：包信息与解析后的依赖关系，具体结构以当前 pnpm 输出为准。

即使直接依赖固定了准确版本，间接依赖仍可能有版本范围，所以锁文件需要提交。

| 内容           | 是否提交 Git     |
| -------------- | ---------------- |
| package.json   | 是               |
| pnpm-lock.yaml | 是               |
| node_modules   | 否，通过安装重建 |

不要手动修改锁文件。添加和升级依赖时，由 pnpm 更新。

以后拉取代码或在自动检查环境中使用：

```bash
pnpm install --frozen-lockfile
```

这是一条安装命令，同时校验依赖声明与锁文件是否一致。不一致时报错，不会自动改写锁文件；它不代替类型检查和测试。

## 第八步：编写共享 TypeScript 配置

在根目录新建 `tsconfig.base.json`：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noEmit": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  }
}
```

| 配置                             | 作用                                                 |
| -------------------------------- | ---------------------------------------------------- |
| target                           | 语言目标为 ES2022，不自动补充缺失的运行时 API        |
| module                           | 采用现代 ES 模块体系                                 |
| moduleResolution                 | Bundler 按适合 Vite、esbuild 的规则查找导入模块      |
| strict                           | 启用严格类型检查，包括隐含 any、空值等检查           |
| noEmit                           | 只检查类型，不生成 JavaScript                        |
| isolatedModules                  | 检查代码是否适合逐文件转译                           |
| verbatimModuleSyntax             | 类型专用导入、导出应明确使用 type                    |
| skipLibCheck                     | 跳过声明文件内部检查，仍检查业务代码使用类型是否正确 |
| forceConsistentCasingInFileNames | 要求路径大小写一致，减少跨系统问题                   |

例如下面的 name 缺少类型，在严格检查下会报错：

```ts
function greet(name) {
  return name.toUpperCase()
}
```

正确写法：

```ts
function greet(name: string) {
  return name.toUpperCase()
}
```

`module` 决定模块体系，`moduleResolution` 决定检查 import 时如何寻找目标。Bundler 允许省略相对导入的文件扩展名，适用于接下来由打包工具处理的界面代码；直接由 Node 执行的代码后续另配模块规则。

职责分工：TypeScript / vue-tsc 检查类型，Vite / esbuild 编译运行文件。这里先不用单独运行根配置，下一步建立实际检查入口。

说明：普通 package.json 是严格 JSON，不支持注释；tsconfig 支持 JSONC，可以写注释帮助学习。

## 第九步：建立 desktop 源文件与检查配置

新建 `apps/desktop/src/renderer/app/metadata.ts`：

```ts
export const appMetadata = {
  name: 'ElabTable',
} as const
```

它保存后续页面会使用的应用名。export 允许导入；as const 将属性收窄为只读字面量类型，不会在运行时冻结对象。

新建 `apps/desktop/tsconfig.json`：

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "types": []
  },
  "include": ["src/renderer/**/*.ts"]
}
```

- extends 路径相对当前配置文件，继承根配置。
- lib 提供 ES2022 与浏览器 API 的类型定义，不是安装运行时功能。
- types 清空自动加入的额外全局类型包，减少 Node 全局类型误入界面代码；这不属于运行时安全隔离，也不会禁止显式导入模块类型。
- include 选择 renderer 下的 TypeScript 文件作为检查入口；导入的其他文件仍可能进入检查范围。

在根目录运行：

```bash
pnpm exec tsc --project apps/desktop/tsconfig.json
```

**完成标志**：无错误输出、返回终端提示符，且没有生成 .js 文件。main、preload 和 Vue 文件的配置留到对应任务。

## 第十步：封装类型检查命令

在 `apps/desktop/package.json` 中新增：

```json
"scripts": {
  "typecheck": "tsc --project tsconfig.json"
}
```

包内脚本以该包目录为工作目录，因此直接指定 tsconfig.json。

在根 `package.json` 中新增：

```json
"scripts": {
  "typecheck": "pnpm -r typecheck"
}
```

`-r` 递归运行工作区子包的同名命令。分别验证：

```bash
pnpm --filter @elabtable/desktop typecheck
pnpm typecheck
```

第一条只检查指定包，第二条检查工作区内配置了该脚本的子包。当前两者最终都运行 desktop 的 tsc。

**完成标志**：两条命令均无错误退出。

## 第十一步：配置格式检查

根目录新建 `.prettierrc.json`：

```json
{
  "singleQuote": true,
  "semi": false,
  "trailingComma": "all",
  "printWidth": 100
}
```

分别表示优先单引号、不写分号、多行结构保留尾逗号、目标行宽 100。JSON 本身仍使用双引号。

根目录新建 `.prettierignore`：

```gitignore
node_modules/
dist/
out/
release/
coverage/
pnpm-lock.yaml
LICENSE
**/整体方案.md
**/规划任务.md
```

上述 **/ 写法明确匹配根目录和子目录中的同名方案文件；原先没有斜杠的文件名规则也可以匹配子目录中的同名文件，不必因文件移入 docs 就认定规则失效。其他工程教学文档正常参与格式检查。

`.prettierignore` 决定哪些文件不格式化；`.gitignore` 决定哪些未跟踪文件不纳入 Git，两者不能互相替代。

将根 `package.json` 的 scripts 补充为：

```json
"scripts": {
  "typecheck": "pnpm -r typecheck",
  "format": "prettier --write .",
  "format:check": "prettier --check .",
  "check": "pnpm typecheck && pnpm format:check"
}
```

- format 会修改文件，执行前知道其范围。
- format:check 只检查，不修改；不符合格式时返回非零退出码。
- check 中的 && 表示前一项成功后才继续下一项。

先检查：

```bash
pnpm format:check
```

出现 `[warn]` 文件列表，说明排版不符合规则，不代表业务逻辑错误。确认范围后修正并复查：

```bash
pnpm format
pnpm check
```

**完成标志**：类型检查成功，且显示 All matched files use Prettier code style!

## 第十二步：让 VS Code 使用项目 Prettier

安装 VS Code 扩展 `Prettier - Code formatter`，扩展标识为 `esbenp.prettier-vscode`。

在根目录新建 `.vscode/settings.json`：

```json
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "prettier.requireConfig": true
}
```

默认使用 Prettier、保存时格式化、要求项目存在配置。扩展在允许加载本地依赖的环境下优先使用项目安装的版本，读取项目配置。

右键“使用…格式化文档”可以确认格式化程序。语言专属设置可能覆盖默认值，遇到某种文件行为不一致时单独检查。

此文件仅含共用格式规则，建议提交 Git，不加入 .gitignore；个人路径和凭据不要写进项目共享设置。

**完成标志**：保存 TypeScript 文件后的格式与 pnpm format 一致。终端 pnpm check 仍是统一验收入口。

## 第十三步：配置 ESLint

### 1. 分清三个工具

| 工具                 | 职责         | 例子                             |
| -------------------- | ------------ | -------------------------------- |
| TypeScript / vue-tsc | 检查类型     | 把字符串传给数字参数             |
| ESLint               | 检查代码问题 | 未使用变量、显式 any、不合法写法 |
| Prettier             | 统一排版     | 缩进、换行、引号                 |

第六步已统一安装所需工具，本步直接编写配置，不重复安装。

02 配置 JavaScript、TypeScript 基础规则；03 在此基础上加入 Vue 模板和脚本规则。ESLint 工具及共享配置统一放根包。

### 2. 编写根配置

根目录新建 `eslint.config.js`：

```js
import js from '@eslint/js'
import { defineConfig } from 'eslint/config'
import tseslint from 'typescript-eslint'
import prettier from 'eslint-config-prettier/flat'

export default defineConfig([
  {
    ignores: ['**/node_modules/**', '**/dist/**', '**/out/**', '**/release/**', '**/coverage/**'],
  },
  {
    files: ['**/*.{js,mjs}'],
    extends: [js.configs.recommended],
  },
  {
    files: ['**/*.{ts,mts}'],
    extends: [js.configs.recommended, tseslint.configs.recommended],
  },
  prettier,
])
```

- 使用现代 flat config，不再创建 .eslintrc 或 .eslintignore。
- 根 package.json 已有 type: module，因此这里可以使用 import/export。
- 单独的 ignores 配置块全局排除生成目录。ESLint 不自动沿用 .gitignore 或 .prettierignore。
- files 控制规则适用的扩展名；后续有 cjs、cts 等文件时再按模块类型补配置。
- extends 引入官方推荐规则；TypeScript 推荐配置会替换不适用于 TS 的 JavaScript 基础规则。
- 本步不启用需要完整类型信息的 typed linting；类型验证仍由 tsc 负责。
- prettier 配置放最后，关闭与 Prettier 冲突的 ESLint 排版规则。它不会执行 Prettier，也不替代 format:check。
- 当前没有浏览器和 Node 全局变量声明，第三项随界面接入浏览器环境，后续 Electron 再按目录加入 Node 环境；不向整个工程开放全部全局变量。

### 3. 配置命令

将根 package.json 的 scripts 整理为以下内容；如果已有其他脚本，保留它们：

```json
"scripts": {
  "typecheck": "pnpm -r typecheck",
  "lint": "eslint . --max-warnings 0",
  "lint:fix": "eslint . --fix --max-warnings 0",
  "format": "prettier --write .",
  "format:check": "prettier --check .",
  "check": "pnpm typecheck && pnpm lint && pnpm format:check"
}
```

lint 只检查；lint:fix 会修改能够自动修正的问题，不能保证全部修好。--max-warnings 0 表示有警告也不通过，防止带着未处理警告交付。

ESLint 由根配置统一管理，直接在根目录执行，不需要给 desktop 再添加同一条 lint 脚本。

运行：

```bash
pnpm lint
```

成功时可能没有额外输出，返回终端提示符即可。遇到错误先读文件、行列号、规则名，不直接关闭规则或用 fix 掩盖原因。

### 4. 确认规则真的生效

可以在 metadata.ts 中临时添加：

```ts
const unusedExample = '验证 ESLint'
```

运行 pnpm lint，预期报告 @typescript-eslint/no-unused-vars。然后删除这行，再次运行应通过。此操作用于理解检查机制，不需要保留示例错误或新增测试文件。

### 5. VS Code 编辑器提示

安装扩展 ESLint，标识为 `dbaeumer.vscode-eslint`。在已有 `.vscode/settings.json` 中补充，保留 Prettier 设置：

```json
"eslint.validate": ["javascript", "typescript"]
```

目前不启用 ESLint 保存自动修复，先理解提示、手动解决；Prettier 仍负责保存格式化。第 03 项加入 Vue 时，再将 vue 添加到 validate 列表。

根目录运行：

```bash
pnpm check
pnpm install --frozen-lockfile
```

验收清单：

- [ ] pnpm 识别根包与 desktop 两个工作区项目。
- [ ] TypeScript 为 6.0.3，依赖没有未解决的兼容警告。
- [ ] pnpm lint 成功，临时未使用变量可以被检出，删除后检查恢复通过。
- [ ] pnpm check 依次完成类型、代码质量和格式三项检查。
- [ ] pnpm install --frozen-lockfile 成功。

pnpm check 包含 ESLint 后，必须以这条完整命令的真实结果验收。教程已写完不表示工程已执行完成。
